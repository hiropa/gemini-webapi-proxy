# Master ↔ slave ("nodes")

Per-account HTTP/SOCKS proxies are unreliable: providers detect datacenter proxies
easily and SOCKS often breaks WebSocket-style traffic. A more reliable way to spread
accounts over several IP addresses is to run **this proxy on each machine** in one
of two modes (`GOP_MODE` in `.env`, chosen by the installer):

- **master** — the instance your clients talk to. It serves `/openai/v1`, holds the
  admin UI you use, and manages **all** account configuration: its own accounts and
  every linked slave's.
- **slave** — a machine that only holds Google accounts. It cannot add, change or
  remove accounts itself (those endpoints answer 403), does not serve `/openai/v1`,
  and has no admin management of its own: it must be **linked by a master**, which
  then drives its accounts over the node API.

```
client ──► master :4982 ──/node/* (Bearer node token, https)──► slave :4982 ──► Google
                           (create/manage accounts, generate)              (from the slave's IP only)
```

## How it works

- **Slave** (`GOP_MODE=slave`): the `/node/*` API is guarded by a *node token*
  (`GOP_NODE_TOKEN`, generated by the installer or at startup, stored in
  `<data_dir>/node_token.txt`, mode 0600). Through it the master can list accounts,
  create, rename, enable/disable, delete them, paste cookies, re-check them, reset
  cooldowns and drive the sign-in flow. The token never exposes cookies — only
  public account data (state, quota, models) crosses the link, plus generated
  images/videos as bytes.
- **Master** (`GOP_MODE=master`): admin UI **Nodes** tab → **Link a node** with the
  slave's URL and token (or `POST /admin/nodes`). Links live in
  `<data_dir>/nodes.json` (mode 0600). The master re-reads each node's accounts
  every `GOP_NODE_REFRESH_INTERVAL` seconds (default 30) and mirrors them as
  accounts named `<node>/<account>` (slot id `<node>::<account>`).
- **Account management**: on the master, the **Accounts** tab edits a slave's
  accounts through `/admin/nodes/{node}/accounts/…` — the same buttons as local
  accounts (enable/disable, rename, delete, paste cookies, check, reset limits),
  forwarded over the link. The Nodes tab has **+ Account** to create an account on
  a slave. A slave's own admin UI refuses account changes: in slave mode it only
  shows status and the sign-in browser (someone must operate the browser on that
  machine; the account itself is created and owned by the master).
- **Requests**: when the pool picks a remote account, the master forwards the
  generation to the slave's `/node/generate`, which runs it through *its own* pool
  pinned to that account (same pacing/concurrency limits as local). Quota (429),
  logged-out (401) and mid-request node failures make the master move on to the
  next account — local or on another node — exactly like local failover. Video
  jobs run on the slave and the mp4 is downloaded to the master via
  `/node/jobs/{id}/content`.

## Media: stored on the master only

Everything a slave generates is forwarded to the master over the link and stored
**only there** — a slave keeps no copies:

- **Images** arrive as base64 in the generate response; the master saves them into
  its gallery (`GOP_IMAGE_KEEP_HOURS`, 90 days by default) with the slave's name in
  the entry (`node`), so the admin UI's **Media** page shows one tab per slave next
  to "This machine". On the slave itself the gallery is a no-op.
- **Videos** run as a job on the slave; the master downloads the mp4 via
  `GET /node/jobs/{id}/content` and then calls `DELETE /node/jobs/{id}`, which
  deletes the slave's file and job record immediately. (If a download never
  happens — the master died mid-handoff — the slave drops the file after an hour
  as a fallback.) The master's Media page lists the video under its slave's tab.

## Egress: a slave's traffic leaves via the slave's IP — only

This is enforced, not just encouraged:

- In slave mode every Google-bound request is created with **no proxy**:
  `GOP_HTTP_PROXY` is ignored (with a warning at startup), per-account proxies from
  `accounts.json` are ignored, and the admin API endpoints that would set one are
  disabled. There is no configuration path that can route a slave's account
  traffic anywhere but out of its own network interface.
- The master never proxies Google traffic for a slave: it only sends
  application-level JSON (prompts, base64 images) over the link, and its own
  `HTTP_PROXY` environment is not used for node connections (`trust_env=False`).

## Setup

1. On each **slave**: `./scripts/install.sh --mode slave` (the installer asks when
   run without the flag; it writes `GOP_MODE=slave` and a fresh `GOP_NODE_TOKEN` to
   `.env` and prints the token). Expose the port over **https** (nginx/Caddy with
   TLS) or an SSH tunnel so the master can reach it.
2. On the **master**: `./scripts/install.sh` (mode `master`), open the admin UI →
   **Nodes** → name, slave URL (`https://slave…:4982`), token → **Link node**.
3. Create accounts on the slave from the master: **Nodes** → **+ Account**, or use
   the **Accounts** tab buttons on the `node/account` entries. Sign in to them via
   the slave's sign-in browser (the "Sign in on …" button opens the slave's admin
   UI) or paste cookies from the master.
4. Link as many slaves as you like; order them with the node priority (lower
   first). Disable/unlink a node any time — its accounts simply leave the
   master's pool (they stay on the slave).

## Security notes

- The link is application-level JSON over HTTPS with a dedicated bearer token — no
  raw TCP/SOCKS forwarding. Use TLS (or an SSH tunnel) so the token and the traffic
  are not readable on the network.
- The node token is separate from `GOP_API_KEY`: a leaked client key cannot drive
  `/node/*`, and the node token cannot call `/openai/v1` (which a slave does not
  serve at all).
- Regenerating the slave's token invalidates all links to it immediately.
- Events `node_down` / `node_up` are emitted (and can be sent to Telegram) when a
  linked node becomes unreachable / reachable again.

## API (for scripts)

Slave, all under `Authorization: Bearer <node token>`:

| Endpoint | Meaning |
|---|---|
| `GET /node/ping` | `{ok, version}` |
| `GET /node/accounts` | local accounts: state, quota, models, cooldowns (public fields only) |
| `POST /node/accounts` | `{name}` — create an account (master-driven) |
| `PATCH /node/accounts/{id}` | `{name?, enabled?, priority?}` |
| `DELETE /node/accounts/{id}` | remove the account |
| `POST /node/accounts/{id}/cookies` | `{cookies}` — paste a cookie string |
| `POST /node/accounts/{id}/check` | re-initialise the client (talks to Google) |
| `DELETE /node/accounts/{id}/cooldowns` | forget the noted limits |
| `POST /node/accounts/{id}/login/start\|finish\|cancel` | drive the sign-in browser on the slave |
| `POST /node/generate` | `{account, model, prompt, images[], mode: chat\|image\|video, seconds?, size?}` → `{text, images:[{b64}], job?, status?}`; errors: 429 `quota`/`unavailable`, 401 `auth`, 403 `refused`, 404 `no_account` |
| `GET /node/jobs/{id}` | video job status (`has_file` when done) |
| `GET /node/jobs/{id}/content` | the mp4 |
| `DELETE /node/jobs/{id}` | the master fetched the mp4: delete the slave's copy and job |

Master, admin session / API key:

| Endpoint | Meaning |
|---|---|
| `GET/POST /admin/nodes`, `PATCH/DELETE /admin/nodes/{id}`, `POST /admin/nodes/{id}/refresh` | manage linked slaves |
| `POST /admin/nodes/{id}/accounts`, `PATCH/DELETE /admin/nodes/{id}/accounts/{acc}`, `…/cookies`, `…/check`, `…/cooldowns`, `…/login/start\|finish\|cancel` | manage a slave's accounts over the link |
| `GET/POST /admin/node-token` | view (masked) / regenerate this instance's slave token |
